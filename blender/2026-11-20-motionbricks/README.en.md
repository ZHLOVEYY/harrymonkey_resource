## What it is

A model that **generates character motion in real time while the game runs**. Give it the
character's last 4 poses (context) and 1–4 poses it should reach (target), and it synthesizes
the motion in between.

That is not the same as "generating a motion clip": it is not text-to-motion and not
video-to-motion. It is **in-betweening** — you give the first and the last keyframe, the
0.6 to 1.9 seconds in the middle are written by the model, and it also decides how long that
middle should take.

One generation is 6–16 tokens, 4 poses per token, at 30 Hz. After playing it, the last 4 poses
become the context of the next generation, so the motion chains into a continuous stream.

## How it works

| Part | What it does | The author's numbers |
|---|---|---|
| root module | Predicts first how many frames the transition takes and the path the pelvis follows | The model picks the duration itself, 6–16 tokens |
| pose module | A masked transformer that predicts motion tokens from the root path plus the constraints | 16 layers, width 1024 |
| decoder | A VQ-VAE that turns discrete tokens back into continuous joint rotations and positions | 8 codebooks of 10 codes each |
| Smart Primitive | Turns behaviors into stackable pieces: interaction box + target poses + action sequence | One set for navigation, one for object interaction, as JSON documents |

Two skeletons share one code path and differ only in the pose layout: **SOMA** (30-joint human)
and **Unitree G1** (34-joint robot). One model covers 350,000+ motion clips; the paper reports
15,000 FPS at 2 ms latency.

My reading (not the author's words):

- **Why it is an in-betweening model rather than a motion generator.** Constraints only apply
  at the two ends: the first 4 poses and at most 4 target poses. Everything in between is
  written by the model from what it learned. So what it gives you is "how to get from A to B",
  not "how this character walks" — the style comes from the training data and from the clips
  inside the smart primitives.
- **It replaces the hardest part of an animation state machine.** The classic problem is the
  combinatorial explosion of state × transition: walk → run → stop → hit → sit down. Each
  combination needs either its own clip or a hand-written transition condition. This hands
  those combinations to a model, and a state only has to declare where its target pose is.
- **Smart Primitive is the part worth learning on its own, and it has nothing to do with the
  neural network.** The objects in a scene (a chair, a railing, a crate) each carry a set of
  keyframes and an interaction range, and the character only has to walk over and line up. A
  normal state machine plus IK can express the same idea; the model is only there to fill the
  middle.
- **The "real time" premise comes from NVIDIA hardware.** The official runtime uses TensorRT
  and the README says it "requires an NVIDIA GPU"; the demos were tested on an RTX 4090.<!-- privacy-scan: allow — the authors' published test GPU, not the owner's machine -->
  The repo's own table gives SOMA FP32 at 2.50 ms and FP16 at 1.28 ms per call (batch 1, the
  same card, Windows). The model itself is ONNX, though, and the documentation explicitly
  supports ONNX Runtime with a fully published tensor contract.

## Why it is worth a look

- **It is the first project to hand the whole "character motion transition" problem to a model
  and release the weights.** The paper's wording is "no foot-locking, no blending, no collision
  detection, no hand-authored transitions", and the UE5 demo runs 2 minutes 40 seconds uncut
  with every motion coming from the same model.
- **The interface is engineering-friendly.** Not text and not tags, but keyframe constraints:
  8 slots (4 context + 4 target) plus three masks, with every tensor shape written down and
  every input and output name given.
- **Zero-shot.** New tasks need no retraining and no tagging; the authors describe it as
  stacking bricks.
- **It is not only about animation.** MotionBricks is now the motion-generation layer inside
  NVIDIA's GR00T whole-body control, and it drives a real Unitree G1 robot.
- **There are already three usable third-party Blender add-ons.** NVIDIA's own repo ships
  **not a single line of Blender code** (I grepped the whole tree: no `blender`, no `mixamo`,
  no `rigify`), but the community has filled that gap:

  | Add-on | What it does | Licence / state |
  |---|---|---|
  | [toyxyz/toyxyz-motion-ai-tool](https://github.com/toyxyz/toyxyz-motion-ai-tool) | Generates and edits SOMA motion in Blender with Kimodo, ARDY and MotionBricks; motion blocks, pose keys, paths and control layers, then FBX export; a Windows companion runs the models locally | GPL-3.0, 52 stars |
  | [Ciellllllllll/motion-creator](https://github.com/Ciellllllllll/motion-creator) | Pick the first and last pose, generate the motion in between, save it as an FBX on a Mixamo skeleton; pin hands/feet/torso/head, add a root bone, export footstep JSON events | No licence file, README in Japanese |
  | [hyun2xyz/motionbricks-blender](https://github.com/hyun2xyz/motionbricks-blender) | Imports MotionBricks `.npz` output as an animated character in Blender, plus a walker script and a recorder | GPL-3.0, 16 stars |

  And [Atomic's custom Blender add-on demo on X](https://x.com/i/web/status/2123694448647590018)
  (2026-11-20) says one-click retargeting to Mixamo and Rigify is "now adding" — **that add-on
  is not open-sourced and has no download link**, and the post had only a handful of views, so
  that route is not shipped.

  Worth calling out on its own: **motion-creator already does MotionBricks → Mixamo-skeleton
  FBX export**, so the step of getting the model's motion onto an existing game character is
  already done by someone in the community — there is no need to wait for Atomic's add-on.

  But all three add-ons **require Windows plus an NVIDIA GPU** (the official runtime goes
  through TensorRT), so without an NVIDIA card this path is still blocked.

- **Things to watch (from the authors' own material):**
  - The official runtime does not run on anything but an NVIDIA card — TensorRT is a hard
    requirement. The repo also has no FBX/glTF export; BVH can be read but not written.
  - The 38 sample motion clips ship under the **NVIDIA Sample Data Evaluation License**:
    evaluation and testing of NVIDIA technologies only, so they cannot be redistributed or
    shipped inside your own game. Wider licensing has to come from the dataset owner
    (BONES-SEED).
  - The model weights are under the NVIDIA Open Model Agreement: commercial use is allowed,
    but read the terms.
  - The SOMA skeleton has only 30 joints and keeps almost no finger detail, which is not enough
    for fine hand animation.
  - All three community add-ons assume Windows plus an NVIDIA card, and one of them
    (motion-creator) has no LICENSE file in the repo — check the terms before using it.
